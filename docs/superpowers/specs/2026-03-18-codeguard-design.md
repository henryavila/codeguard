## 1. What Is CodeGuard

CodeGuard is an AI-native code governance system. It installs via `npx`, configures via AI conversation, and enforces quality through three complementary layers: deterministic tools (Larastan, Pint, PHPMD), architectural rules (Pest), and AI-powered semantic analysis.

**Core thesis:** The real value is not running PHPStan — any dev can do that. The value is an AI that understands the project's architecture and identifies violations that no static tool can detect.

**Value hierarchy:**
1. **Core** — AI semantic analysis (pattern violations only AI can see)
2. **High** — Prevention (CODEGUARD.md guides AI during code generation)
3. **Base** — Deterministic tools + Pest arch tests (safety net)

## 2. Architecture Overview

### Skills-First

The AI agent inside the developer's IDE does the heavy lifting. The npm package is a delivery vehicle.

```
npm package (delivery vehicle)
├── installer          → copies skills to IDEs + hook runner and modules to .codeguard/
├── hook runner        → deterministic tools on git diff (no AI)
├── skills/            → codeguard-setup.md, codeguard-run.md, codeguard-health.md (the product)
├── modules/
│   ├── core/
│   │   ├── patterns/          → universal patterns (SOLID, DDD, etc.)
│   │   └── ai-rules/          → universal AI analysis instructions
│   ├── php/
│   │   ├── patterns/          → PHP-specific patterns
│   │   └── ai-rules/          → PHP AI analysis instructions
│   └── php-laravel/
│       ├── module.yaml        → identity, detection
│       ├── preset.yaml        → tool defaults
│       ├── patterns/          → Laravel patterns (YAML)
│       └── ai-rules/          → Laravel AI analysis instructions (markdown)
├── src/adapters/
│   └── php-laravel/           → tool adapters (TypeScript, compiled by tsdown)
└── package.json
```

### Three-Layer Enforcement

| Layer | Tool | Catches | Precision | Runs in |
|---|---|---|---|---|
| Deterministic tools | Larastan, Pint, PHPMD | Types, formatting, smells | 100% | Hook (pre-commit) |
| Architectural rules | Pest arch testing | Structure, deps, naming | 100% | Hook (pre-commit) |
| Semantic analysis | CodeGuard AI | Pattern drift, missing DTOs, logic in wrong layer | Probabilistic | `/codeguard-run` skill |

## 4. Module System — Extensibility

### Structure

```
modules/{module-name}/           # static data, shipped as-is
  ├── module.yaml                # identity, detection heuristics, capabilities
  ├── preset.yaml                # tool configs, install commands
  ├── patterns/                  # pattern catalog (YAML) — AI consumes
  └── ai-rules/                  # analysis instructions (markdown) — AI consumes

src/adapters/{module-name}/      # TypeScript, compiled by tsdown
  ├── larastan.ts                # hook runner consumes
  ├── pint.ts
  └── ...
```

**Note:** `module.yaml` and `preset.yaml` are only present in leaf modules that define tool capabilities (e.g., `php-laravel/`). Intermediate layers (`core/`, `php/`) contain only `patterns/` and `ai-rules/` — they have no tool integrations to configure. See the Section 2 tree for the accurate per-layer structure.

Note: Pest arch tests are generated by the setup skill from active patterns' verification rules — no templates needed in the module structure.

### Two extensibility layers

| Layer | Files | Language | Barrier | Who contributes |
|---|---|---|---|---|
| Patterns + AI rules | `modules/{name}/patterns/*.yaml` + `ai-rules/*.md` | YAML + Markdown | Low | Anyone |
| Tool adapters | `src/adapters/{name}/*.ts` | TypeScript | Higher | Node.js devs |

### Module hierarchy

```
modules/
  ├── core/              # always loaded — universal patterns
  ├── php/               # loaded for any PHP project
  └── php-laravel/       # loaded when Laravel detected
```

When the community creates `javascript-react/`, it inherits `core/` patterns automatically.

**Resolution mechanism:** When the setup skill detects a leaf module (e.g., `php-laravel`), it resolves the full chain using the module's `language` field from `module.yaml`:

1. `core/` — always loaded (hardcoded)
2. `{language}/` — loaded if directory exists (e.g., `php/` from `language: php`)
3. `{language}-{framework}/` — the detected leaf module itself (e.g., `php-laravel/`)

The `/codeguard-run` skill uses the same chain to load `patterns/` and `ai-rules/` from all layers. The hook runner does not use this chain — module data is compiled into the bundle at build time.

### module.yaml

```yaml
name: php-laravel
label: Laravel
language: php
framework: laravel

detection:
  files:
    - composer.json
    - artisan
  dependencies:
    - laravel/framework
  confidence: high

  static-analysis:
    tool: larastan
    default_level: 6
  formatting:
    tool: pint
    preset: laravel
  mess-detection:
    tool: phpmd
    rulesets: [unusedcode, codesize]
  arch-testing:
    tool: pest
    presets: [php, laravel]
```

### preset.yaml

```yaml

  larastan:
    binary: vendor/bin/phpstan
    config: phpstan.neon
    level: 6
    extensions: [larastan]
  pint:
    binary: vendor/bin/pint

  phpmd:
    binary: vendor/bin/phpmd
    config: phpmd.xml

    binary: vendor/bin/pest
    directory: tests/Architecture

  - composer require --dev larastan/larastan
  - composer require --dev laravel/pint
  - composer require --dev phpmd/phpmd
  - composer require --dev pestphp/pest
```

### ToolAdapter interface

Current `ToolAdapter` in `src/core/types/modules.ts` (updated in Phase 1 from a single `analyze()` method). The interface separates concerns for the hook runner's needs:

```typescript
export interface CommandSpec {
  binary: string;
  args: string[];
  cwd?: string;
  timeout?: number;
}

export interface ToolAdapter {
  readonly name: string;
  readonly binary: string;
  readonly supportsFix: boolean;
  buildCommand(files: string[], config: ToolConfig): CommandSpec;
  parseOutput(raw: string): ToolResult;
  filterToStaged(violations: AnalysisViolation[], stagedFiles: string[]): AnalysisViolation[];
}
```

## 5. Capabilities Model

User configures **capabilities**, the module resolves to **tools**:

```
"static-analysis" + Laravel  → Larastan
"static-analysis" + React    → ESLint
"formatting"      + Laravel  → Pint
"formatting"      + React    → Prettier
"arch-testing"    + Laravel  → Pest (laravel preset)
"arch-testing"    + React    → ESLint plugin + custom
```

### MVP capabilities (Laravel)

| Capability | Tool | Enforcement | Hook? |
|---|---|---|---|
| `formatting` | Pint | Autofix | Yes — auto-corrects staged files |
| `static-analysis` | Larastan | Block/Warn | Yes — full project, filter to staged |
| `mess-detection` | PHPMD | Warn | Yes — staged files only |
| `arch-testing` | Pest | Block | Yes — arch test suite (generated file + built-in presets) |
| `ai-review` | CodeGuard AI | Block/Warn | No — only via `/codeguard-run` |

**Note:** `ai-review` is not listed in `codeguard.yaml` because it has no tool adapter and no hook runner involvement. It is always available via `/codeguard-run` — the AI agent performs this analysis directly using patterns + ai-rules.

**Enforcement restriction:** `autofix` enforcement is only valid for capabilities whose tool can modify files (currently only `formatting` / Pint). The setup skill must validate this — if a user tries to set `static-analysis.enforcement: autofix`, warn and default to `block`. The hook runner also validates at startup using `adapter.supportsFix`: if a non-fixable capability has `autofix`, treat it as `warn` and print a warning.

### Roadmap capabilities

| Capability | Tool | What it does |
|---|---|---|
| `modernization` | Rector | Automated refactoring, version upgrades |
| `security` | Pest security preset | No eval, md5, sha1, unsafe unserialize |
| `mutation-testing` | Infection | Test quality measurement |

## 6. Pattern Catalog

Full analysis: [2026-03-18-pattern-catalog-analysis.md](2026-03-18-pattern-catalog-analysis.md)

### Three-layer structure

| Layer | Scope | MVP Count |
|---|---|---|
| `core/` | Universal (SOLID, Clean Code, DDD, GoF, Arch Fitness) | 13 |
| `php/` | PHP-specific | 6 |
| `php-laravel/` | Laravel-specific | 9 |
| **Total** | | **28** |

### MVP patterns summary

**Core (13):** SRP, DRY, Small Functions, Few Arguments, Consistent Error Handling, Separation of Concerns, No Long Switch/If Chain, No Constructor With Too Many Params, No God Object, No Deep Inheritance, Layer Dependency Direction, No Circular Dependencies, Bounded Contexts

**PHP (6):** Strict Typing, No HTML in PHP, No Debug Functions, Type Declarations, Exception Handling, No Superglobals

**Laravel (9):** Service Layer, DTOs, Form Requests, Action Classes, Value Objects, Resource Controllers, Policies, No env() outside config, No Logic in Blade

**Note on Repositories pattern:** The pattern catalog classifies Repositories as "MVP (for stacks that use them)." For the Laravel module, the Repository pattern is NOT included because Laravel's Eloquent already serves this role. The Service Layer pattern handles the boundary instead. For other PHP modules (e.g., Symfony), Repositories would be MVP.

### Roadmap patterns: 20 additional (see full analysis)

### Pattern YAML schema

```yaml
name: service-layer
description: Controllers delegate business logic to Services
category: framework
layer: laravel
severity: critical
classification: mvp

detection:
  signals:
    - type: directory
      value: app/Services
    - type: import
      value: "App\\Services\\*"
  confidence: high

verification:
  rules:
    - controllers must not access Eloquent models directly
    - controllers must not contain business logic
    - services must not return HTTP responses
    - services must not access Request object

examples:
  correct: |
    $result = $this->orderService->create(OrderData::from($request));
  violation: |
    $order = Order::create($request->all());

related_patterns:
  - dto
  - form-requests
```

### How patterns are used

- **Setup skill:** Loads all pattern YAMLs from module layers → presents to dev for validation
- **Run skill:** AI analyzes code against active patterns' verification rules
- **Pest arch tests:** The generated `CodeGuardArchTest.php` contains two kinds of tests: (1) built-in preset calls like `arch()->preset()->php()` and `arch()->preset()->laravel()` controlled by `CapabilityConfig.presets`, and (2) custom `arch()->expect()` rules generated from active patterns' structural verification rules. Both are embedded in the PHP file at setup time — the hook runner just executes `vendor/bin/pest tests/Architecture/` without needing to know about presets
- **CODEGUARD.md:** Active patterns become AI context for code generation
- **codeguard.yaml:** The `patterns.catalog` list contains framework-specific patterns selected during setup. Core and language-layer patterns (from `modules/core/` and `modules/php/`) are loaded automatically based on the module hierarchy and are NOT listed individually in `codeguard.yaml`. These patterns are always active and cannot be excluded — they represent fundamental quality standards (SOLID, Clean Code, PHP best practices) that form the safety net. Phase 3 of setup ("dev adds/removes/adjusts patterns") applies only to framework-specific patterns in `patterns.catalog`.
- If a pattern name appears at multiple layers, the most specific module takes precedence: leaf module > language layer > core (e.g., `php-laravel/` patterns override `php/` which override `core/`). Currently all patterns have unique names; this rule applies when community modules override a core pattern (e.g., a `php-symfony` module overriding `exception-handling` from `php/`).
- Discovered and custom pattern YAMLs stored in `.codeguard/patterns/` (project-local, not in module)

## 7. Configuration

### codeguard.yaml

```yaml
version: "1.0"

project:
  language: php
  framework: laravel
  module: php-laravel

capabilities:
  static-analysis:
    enabled: true
    level: 6
    enforcement: block
  formatting:
    enabled: true
    enforcement: autofix   # autofix = silently correct, never block
  mess-detection:
    enabled: true
    enforcement: warn
  arch-testing:
    enabled: true
    enforcement: block
    presets: [php, laravel]

patterns:
  # catalog lists only framework-specific patterns selected during setup.
  # Core and language-layer patterns (modules/core/, modules/php/) are loaded
  # automatically based on module hierarchy and NOT listed here.
  catalog:
    - service-layer
    - dto
    - form-requests
    - action-classes
    - value-objects
    - resource-controllers
    - policies
    - no-env-outside-config
    - no-logic-in-blade
  # discovered/custom patterns are stored as YAML files in .codeguard/patterns/
  # using the pattern name as filename (e.g., .codeguard/patterns/result-objects.yaml)
  discovered:
    - result-objects
  custom:
    - our-internal-rule

thresholds:
  max_method_lines: 20
  max_indentation_levels: 2

hooks:
  pre-commit:
    enabled: true

baseline:
  path: .codeguard/baseline.json
```

### Config precedence

`codeguard.yaml` overrides `preset.yaml` defaults. Two different consumers read the config:

**Hook runner merge** (produces `ToolConfig` for each adapter):

1. `preset.yaml` → base defaults (`binary`, `config`, `rulesets`, `extensions`, `directory`)
2. `module.yaml` capabilities → tool defaults (`default_level`)
3. `codeguard.yaml` capabilities → user overrides (`enabled`, `enforcement`, `level`)

Only fields that exist in `ToolConfig` flow through this merge. Fields like `presets` in `CapabilityConfig` are **not consumed by the hook runner** — they are consumed by the setup skill (see below).

**Setup skill reads** (generates files, not runtime merge):

- `CapabilityConfig.presets` → which Pest `arch()->preset()` calls to embed in the generated `CodeGuardArchTest.php`
- `ModuleCapability.preset` (singular) → Pint preset name, written to tool config files

Example: preset.yaml has `larastan.level: 6`, user sets `capabilities.static-analysis.level: 9` in codeguard.yaml → Larastan runs at level 9.

### Change flow

- **Small change** (e.g., Larastan level 6→9, threshold adjustment): edit YAML directly → hook/AI uses it on next run
- **Big change** (add patterns, change stack): re-run `/codeguard-setup` → AI re-analyzes everything

**Intentional limitation:** `CapabilityConfig` exposes only `enabled`, `enforcement`, `level`, and `presets`. Lower-level fields like `rulesets`, `config`, `extensions`, and `directory` are not user-configurable via `codeguard.yaml` — they come from `preset.yaml` defaults. This keeps the user-facing config simple. If a user needs to override these, they edit the tool's own config file (e.g., `phpmd.xml`) directly.

### CODEGUARD.md

Generated by AI during setup. Project-specific, not template-based.
- Read automatically by AI IDEs as context for code generation
- Contains: architecture patterns, naming conventions, file organization, tool config summary
- Enriched over time by `/codeguard-setup` re-runs

### Baseline

```json
{
  "version": "1.0",
  "generated": "2026-03-18T10:30:00Z",
  "generatedBy": "codeguard-run",
  "module": "php-laravel",
  "entries": [
    {
      "tool": "larastan",
      "rule": "method.notFound",
      "file": "app/Services/OrderService.php",
      "message_normalized": "Call to undefined method * on *",
      "hash": "a1b2c3d4"
    }
  ]
}
```

- Generated by `/codeguard-run` (AI skill)
- Consumed by hook runner (Node.js)
- Matching: by `hash` — deterministic hash of `tool + rule + file + message_normalized` (four fields). Strips line numbers, so violations survive code movement within a file. File renames invalidate baseline entries (the `file` field changes) — this is acceptable for MVP; stale entries are harmless (ignored, not matched)
- The hook runner computes the same hash for each new violation and checks if it exists in the baseline
- Date format: baseline JSON uses ISO 8601 (`2026-03-18T10:30:00Z`) for precision on when the baseline snapshot was taken

## 8. Hook Runner

### Architecture

Self-contained bundle at `.codeguard/hook-runner.js`, committed to repo.
The bundle is pre-compiled during `npm run build` as a tsdown entry point. Ships as `dist/hooks/runner.js` in the npm package. During `npx codeguard install`, the CLI copies it to `.codeguard/hook-runner.js`. No runtime compilation needed.

**Pending build change:** `tsdown.config.ts` must add bundling options for the `hooks/runner` entry point so that all adapter dependencies are inlined into a single self-contained file. The current config builds it as a plain ESM module without dependency bundling.

```
.git/hooks/pre-commit (shell shim):
│   #!/bin/sh
│   exec node "$(dirname "$0")/../.codeguard/hook-runner.js"
│
  └── .codeguard/hook-runner.js (Node.js bundle, includes adapters)
        ├── reads codeguard.yaml
        ├── gets staged files (git diff --cached)
        │
        ├── STAGE 1: Autofix (sequential, before analysis)
        │   └── Pint (staged files → fix → git add fixed files)
        │
        ├── STAGE 2: Analysis (parallel via Promise.allSettled)
        │   ├── Larastan (full project → filter to staged)
        │   ├── PHPMD (staged files)
        │   └── Pest arch tests (tests/Architecture/)
        │
        ├── normalizes violations
        ├── applies baseline matching
        ├── formats tool-level messages
        └── exit code decision
```

### Execution order

**Pint runs FIRST, alone.** It modifies and re-stages files. Only after Pint completes do the analysis tools run. This prevents race conditions — Larastan, PHPMD, and Pest all analyze the already-formatted code.

### Exit code logic

```
For each violation after baseline matching:
  if enforcement == 'block' AND not baselined → BLOCKING
  if enforcement == 'warn'  → WARNING (printed, not blocking)
  if enforcement == 'autofix' → already fixed by Pint, not a violation

Autofix validation (before tool execution):
  For each capability with enforcement == 'autofix':
    if adapter.supportsFix == false → override to 'warn', print warning
  This runs at startup, so the rules above never see 'autofix' on a non-fixable tool

Autofix failure:
  if Pint exits non-zero → print error, treat as WARNING (not blocking)
  Rationale: a formatting failure should not block the commit; the dev
  can fix manually or investigate

Tool execution failure (installed but crashes):
  Print "⚠ {tool} failed: {stderr}" as WARNING
  Continue with remaining tools (partial results)

Missing codeguard.yaml:
  Exit 1 with "codeguard.yaml not found — run /codeguard-setup first"
  This is an error state: the hook was installed but config is missing

Hook disabled (hooks.pre-commit.enabled is false in codeguard.yaml):
  Exit 0 immediately — skip all tools silently

Missing baseline file (.codeguard/baseline.json not found):
  Treat as empty baseline (no entries) — all violations are new
  Print "ℹ No baseline found — run /codeguard-run to establish baseline"
  This is the normal state between /codeguard-setup and first /codeguard-run

Exit code:
  Any BLOCKING violations exist → exit 1 (commit blocked)
  Only WARNINGs (including tool failures) → exit 0 (commit proceeds, warnings printed)
  All clean → exit 0 (commit proceeds)
  All tools failed to run → exit 1 (never silently succeed)
```

### Capability → adapter resolution

The hook runner reads `codeguard.yaml` (which uses capability names like `static-analysis`, `formatting`) and must resolve these to concrete tool adapters (larastan, pint). Resolution flow:

1. Read `project.module` from `codeguard.yaml` (e.g., `php-laravel`)
2. The module's capability→tool mapping is **compiled into the bundle** during build:
   - A **build-time codegen script** (pre-build step) reads each `modules/*/module.yaml` and `modules/*/preset.yaml` where they exist (only leaf modules with tool capabilities — e.g., `php-laravel/` but not `core/` or `php/`) and generates a TypeScript registry file (e.g., `src/hooks/generated/module-registry.ts`) containing the parsed data as typed constants
   - tsdown bundles this generated file into `hook-runner.js` along with the adapters
   - This eliminates runtime YAML parsing for module/preset data. The hook runner still needs a YAML parser for `codeguard.yaml` at runtime — the `yaml` npm package is bundled by tsdown for this purpose
3. For each enabled capability, look up the registered adapter by tool name
4. Merge config in order: compiled `PresetTool` defaults → compiled `ModuleCapability` defaults → `CapabilityConfig` from `codeguard.yaml` (user overrides like `level: 9`). Only `ToolConfig`-compatible fields flow through (see Config precedence above)

This means adding a new module requires rebuilding the npm package — which is the expected flow since modules ship inside the package.

### Key decisions

- **Self-contained bundle** — works without npm install, committed to repo
- **Adapters bundled in** — pre-compiled during `npm run build` into a self-contained bundle, `install` copies it to `.codeguard/`
- **ToolAdapter interface** — no hardcode, even for MVP
- **Tool-level messages only** — no pattern knowledge in hook
- **OutputFormatter interface** — the hook runner uses `OutputFormatter` to format findings, errors, and summaries for terminal output. Skills follow the same output format by convention for consistency
- **Partial results** — one tool failing doesn't suppress others (Promise.allSettled)
- **Tool not installed** — adapter detects missing binary, reports clear error with install command, continues with remaining tools
- **Larastan runs full project** — filters output to staged files (PHPStan needs full context)
- **Pint autofixes** — corrects and re-stages before commit proceeds

## 12. Skill Flow Outlines

Skill file contents are defined during implementation. High-level flows:

### /codeguard-setup

```
1. Scan available modules (read all module.yaml files from .codeguard/modules/)
2. Detect stack (run detection heuristics from each module.yaml against project files)
```

## 13. Thresholds Ownership

`thresholds` in codeguard.yaml define limits. Each threshold maps to the enforcement layer that can check it:

| Threshold | Pest (deterministic) | AI (semantic) |
|---|---|---|
| `max_method_lines: 20` | No per-method assertion in Pest (`toHaveLineCountLessThan` is per-class) | AI flags methods over 20 lines with richer context ("this method does X, Y, Z — consider extracting") |
| `max_indentation_levels: 2` | Not natively supported by Pest | AI detects deep nesting and suggests flattening |

Both MVP thresholds are AI-only — Pest has no per-method line count or per-nesting-depth assertion. Class-level thresholds (if added) could use Pest's `toHaveLineCountLessThan`.

**Classification criteria for setup skill** — when generating Pest arch tests from pattern verification rules:

| Goes to Pest (deterministic) | Stays AI-only (semantic) |
|---|---|
| Rules about **namespaces, imports, class types** (`controllers must not use Eloquent directly` → `arch()->expect('App\Http\Controllers')->toNotDependOn('Illuminate\Database\Eloquent')`) | Rules about **intent or behavior** (`controllers must not contain business logic` — "business logic" requires semantic understanding) |
| Rules about **file/directory structure** (`services must not return HTTP responses` → `arch()->expect('App\Services')->toNotDependOn('Illuminate\Http')`) | Rules about **code quality** (`methods should be short and focused`) |
| Rules about **naming conventions** | Rules about **missing abstractions** (`should use DTOs instead of arrays`) |
| Rules expressible as `toOnlyUse`, `toNotDependOn`, `toExtend`, `toImplement`, `toHavePrefix/Suffix`, `toBeClasses/Interfaces/Enums` | Everything else |

The setup skill applies this heuristic: if the rule can be expressed as a Pest `arch()` expectation using dependency/structure/naming assertions, it goes to Pest. If it requires reading and understanding code semantics, it stays as an AI verification rule.
